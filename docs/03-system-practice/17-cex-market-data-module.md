# 第十七章：CEX 行情数据模块——K 线、成交与订单簿

## 17.1 行情不是下载一次就结束的文件

第四章使用 CCXT 获取了第一份 BTC 日线数据。那次实验解决的是“如何读到数据”，而一个持续运行的研究系统还要回答更多问题：

```text
程序启动前的历史数据从哪里来？
启动后的新数据怎样持续写入？
网络中断期间漏掉的数据怎样恢复？
重复收到同一根 K 线怎么办？
当前 K 线尚未闭合时能否用于回测？
两家交易所的周期、字段和时间边界是否相同？
```

单次下载得到的是一份样本，行情模块维护的却是一条不断向前延伸的时间序列。前者运行成功一次即可结束，后者必须长期面对断线、限流、重复、乱序、空响应和交易所规则变化。

因此，CEX 行情模块的目标不是“尽可能快地保存所有消息”，而是建立一份可以被研究使用的数据事实：来源明确、字段统一、时间连续、重复可控、异常可见。

## 17.2 K 线、成交和订单簿观察的是三个层次

CEX 常见公开行情可以分为 K 线、逐笔成交和订单簿。

| 数据类型 | 表达的内容 | 典型用途 | 主要难点 |
|---|---|---|---|
| K 线 | 一段时间内的开高低收与成交量 | 趋势、指标、低中频回测 | 周期边界、未闭合数据、历史缺口 |
| 逐笔成交 | 撮合引擎已经完成的每一笔公开成交 | 成交方向、订单流、短期冲击 | 数据量大、历史窗口有限、去重 |
| 订单簿 | 某一时刻尚未成交的买卖挂单 | 点差、深度、滑点和流动性 | 快照与增量衔接、序号连续性、无法事后完整补回 |

三者不是彼此替代的关系。

K 线是成交数据的时间聚合。它适合计算均线、收益率和波动率，但会隐藏一根 K 线内部的成交顺序。逐笔成交保留了成交价格和数量，却看不到当时还有多少挂单等待成交。订单簿展示潜在流动性，但挂单可以随时撤销，并不代表这些数量最终都会成交。

当前系统已经完成 K 线的实时订阅、REST 补数、幂等存储和状态查询。逐笔成交与订单簿在本章中给出数据结构和接入原则，尚未写成持久化生产模块。明确区分“已经实现”和“已经设计”，是开源研究记录应有的准确性。

## 17.3 为什么第一版只选择现货 BTC/USDT

同一个交易所可能同时提供现货、永续合约、交割合约、期权和杠杆市场。它们都可能出现 `BTC` 和 `USDT`，但价格、成交量、资金成本和风险完全不同。

第一版采集器把范围限制为：

```text
交易所：Binance、OKX
市场：现货
交易对：BTC/USDT
数据：已经闭合的 K 线
```

这样做有三个原因。

第一，BTC/USDT 流动性较高，数据结构相对稳定，适合验证采集链路。第二，现货不需要在数据层同时处理资金费率、标记价格、指数价格和合约到期。第三，两家交易所同时采集，可以及时发现某些问题究竟来自市场本身，还是来自单一数据源。

“BTC/USDT”也必须和交易所原生标识区分。CCXT 使用统一形式 `BTC/USDT`，Binance WebSocket 使用小写标识 `btcusdt`，OKX 使用 `BTC-USDT`。系统内部统一保存 `BTC/USDT`，适配器负责转换交易所格式。

## 17.4 一根闭合 K 线包含什么

系统使用统一的 `Candle` 对象表达 K 线：

| 字段 | 含义 |
|---|---|
| `exchange` | 数据来自哪家交易所 |
| `symbol` | 统一交易对，例如 `BTC/USDT` |
| `timeframe` | 周期，例如 `1m`、`1h`、`1d` |
| `open_time` | K 线开始时间 |
| `close_time` | K 线结束时间 |
| `open` | 开盘价 |
| `high` | 最高价 |
| `low` | 最低价 |
| `close` | 收盘价 |
| `volume` | 该周期成交量 |
| `trade_count` | 成交笔数，交易所未提供时为空 |
| `is_closed` | 是否已经闭合 |
| `source` | `websocket` 或 `rest` |
| `source_event_time` | 交易所消息时间，无法取得时为空 |
| `received_at` | 系统收到或拉取数据的时间 |

价格和数量使用 `Decimal` 进入数据库，而不是依赖二进制浮点数表达。数据库分别使用高精度 `Numeric` 字段保存价格和成交量，减少序列化和多次计算造成的精度误差。

K 线还要通过基础一致性检查：

```text
close_time 必须晚于 open_time
high 不能低于 open 或 close
low 不能高于 open 或 close
high 不能低于 low
volume 不能为负数
```

这些检查不能证明行情完全正确，却能在异常消息进入研究数据前阻止明显错误。

## 17.5 为什么只保存已经闭合的 K 线

一根正在形成的 K 线会不断变化。当前价格上涨时，最高价可能被刷新；新的成交出现后，收盘价和成交量也会改变。

如果系统每次收到更新都把当前 K 线当成最终结果，策略可能在同一根 K 线上反复改变信号。历史回测读取到的最终 K 线，与实时时刻曾经看到的中间状态也会不同。

因此，当前采集器只持久化闭合 K 线：

```text
Binance：kline.x == true
OKX：confirm == "1"
```

这项规则让数据更适合第 5—8 章的低中频研究。它也意味着数据库不会每秒增加一根 `1m` K 线：一分钟周期通常每分钟增加一条，小时周期每小时增加一条。

未闭合数据并非没有价值。实时交易界面、盘中风控和高频策略可能需要保存其变化过程，但那是另一种数据模型，不能和最终闭合 K 线混在同一张表里。

## 17.6 所有研究时间统一为 UTC

当前系统默认采集：

```text
1m、5m、15m、1h、4h、1d、1w
```

数据库中的时间统一按照 UTC 理解。假设数据库显示：

```text
2026-07-19 06:57:00
```

它对应新加坡时间：

```text
2026-07-19 14:57:00（UTC+8）
```

统一 UTC 可以避免服务器部署地区、浏览器语言和操作系统时区改变 K 线边界。日线和周线尤其需要明确边界。OKX 适配器使用 `1Dutc` 和 `1Wutc`，周线按 UTC 的周一零点开始。

不同周期的“最新数据”不能直接用当前时刻判断。若当前时间是 `06:57 UTC`：

```text
1m 最新闭合 K 线开盘时间：06:56
5m 最新闭合 K 线开盘时间：06:50
15m 最新闭合 K 线开盘时间：06:30
1h 最新闭合 K 线开盘时间：05:00
4h 最新闭合 K 线开盘时间：00:00
```

一条小时线停留在 `05:00`，不代表采集延迟了近两小时。它从 `05:00` 开始，到 `06:00` 才闭合；`06:00` 这根仍在形成，要到 `07:00` 才能写入。

## 17.7 为什么同时使用 WebSocket 和 REST

WebSocket 和 REST 分别解决不同问题。

```text
                    ┌──WebSocket──> 持续接收新闭合 K 线
交易所公开行情 ────┤
                    └──REST───────> 初始化历史数据与修复缺口
                                      │
                                      ↓
                              字段标准化与校验
                                      │
                                      ↓
                                MySQL 幂等写入
```

只使用 REST 轮询，逻辑容易理解，但需要不断请求交易所，数据到达时间也取决于轮询间隔。只使用 WebSocket，可以及时收到新数据，却无法自动取得程序启动前的历史记录，也无法保证断线期间的消息能够重新推送。

两条路径结合后，WebSocket 负责“向前延伸”，REST 负责“向后补齐和向中间修复”。无论数据来自哪条路径，最终都转换为同一个 `Candle` 对象并写入同一张表。

## 17.8 Binance 实时订阅

Binance 适配器把内部周期转换为类似下面的订阅名称：

```text
btcusdt@kline_1m
btcusdt@kline_5m
btcusdt@kline_1h
```

收到消息后，解析器首先检查事件类型和 `x` 字段，只处理闭合 K 线。消息中的交易所事件时间进入 `source_event_time`，本机处理时间进入 `received_at`，两者可以用于分析网络和处理延迟。

Binance WebSocket 连接存在生命周期限制，因此采集器会在接近 24 小时时主动轮换连接。断线后，系统先记录状态和重连次数，再通过 REST 检查空档，随后使用指数退避重新建立连接。

公开 REST 数据使用 Binance 的现货数据端点，并把 CCXT 市场加载限制为现货，避免在只研究 BTC/USDT 现货时额外访问合约市场。

## 17.9 OKX 实时订阅

OKX 的 K 线频道使用 Business WebSocket。内部周期与频道名称存在映射关系：

```text
1m  → candle1m
1h  → candle1H
1d  → candle1Dutc
1w  → candle1Wutc
```

OKX 要求连接在长时间没有数据时发送字符串 `ping`，并等待 `pong`。采集器在等待超时后主动发送心跳；若未得到响应，则把连接视为异常，由外层重连流程接管。

OKX 的交易对标识使用 `BTC-USDT`。收到消息后，系统根据频道名称恢复内部周期，再检查确认字段，只把最终闭合记录转换为 `Candle`。

不同交易所的适配器看起来增加了代码量，却把差异挡在了系统入口。数据库、策略和回测只处理统一字段，不需要到处编写 `if exchange == ...`。

## 17.10 初始补数从哪里开始

第一次启动时，数据库没有采集进度。系统先计算“当前周期最近一根应当闭合的 K 线”，再向前回溯一定数量。

默认配置为：

```text
COLLECTOR_INITIAL_LOOKBACK_CANDLES=1000
COLLECTOR_BACKFILL_PAGE_SIZE=300
COLLECTOR_BACKFILL_MAX_PAGES=20
```

`1000` 表示目标回溯数量，不代表交易所一定能够返回 1000 条。例如，某交易对只有 465 根有效周线，那么 465 条就是完整可用历史，而不是数据不足。

REST 返回数量还受到交易所单次上限影响，因此补数必须分页。每一页从上一页最后一根 K 线之后继续，直到达到最近应当闭合的时间、接口不再返回数据，或者达到最大分页次数。

补数过程会过滤尚未闭合的当前 K 线。CCXT 返回的最后一根 OHLCV 可能仍在形成，不能因为它出现在 REST 响应中就直接视为历史事实。

## 17.11 持续补数不是重复下载 1000 根数据

初始化完成后，采集检查点记录每个数据流的最新闭合时间。一个数据流由三项信息确定：

```text
exchange + symbol + timeframe
```

系统默认每 60 秒进行一次巡检，并检查最近 500 根 K 线：

```text
COLLECTOR_GAP_LOOKBACK_CANDLES=500
COLLECTOR_RECONCILE_INTERVAL_SECONDS=60
```

如果最新记录早于检查窗口，系统从最新记录的下一期继续补齐。如果最新时间看起来正常，系统仍会扫描窗口内部，寻找是否缺少某个中间时间点。

例如，数据库中存在：

```text
12:00
12:01
12:03
12:04
```

只比较最大时间会认为数据已经更新到 `12:04`，但内部仍缺少 `12:02`。缺口扫描会从 `12:02` 开始重新请求，已存在的后续 K 线通过幂等写入更新，不会产生重复行。

## 17.12 唯一键和幂等写入

交易所可能重复推送消息，REST 补数也可能覆盖 WebSocket 已写入的时间范围。如果数据库只执行普通插入，同一根 K 线会出现多条记录。

行情表使用以下字段构成唯一身份：

```text
exchange + symbol + timeframe + open_time
```

MySQL 使用原子 upsert：记录不存在时插入，已经存在时更新同一行。这样，同一段补数可以安全重试，WebSocket 与 REST 在时间边界发生重叠时也不会制造重复数据。

“没有重复”只是幂等写入解决的问题之一。系统仍要判断两次收到的字段是否一致。如果同一交易所在同一开盘时间返回不同 OHLCV，应该记录差异，而不是默认最后一次一定正确。当前版本以最新有效值更新，后续可以增加原始消息留存或修订审计表。

## 17.13 采集检查点记录什么

`ingestion_checkpoints` 为每条数据流保存运行状态：

| 字段 | 用途 |
|---|---|
| `status` | `starting`、`connecting`、`live`、`ready`、`degraded` 或 `disconnected` |
| `last_closed_open_time` | 最新已保存闭合 K 线的开盘时间 |
| `last_received_at` | 最近收到数据的时间 |
| `last_persisted_at` | 最近成功写入数据库的时间 |
| `last_backfill_at` | 最近完成 REST 检查的时间 |
| `reconnect_count` | WebSocket 重连次数 |
| `backfilled_candles` | REST 处理的补数记录数量 |
| `last_error` | 最近一次异常信息 |

检查点让程序重启后能够继续工作，也让数据中心页面可以展示采集状态。但状态字段不能代替数据质量检查。

`live` 主要表示 WebSocket 已经连接。某个长周期可能刚刚连接，还没有等到下一根闭合 K 线；REST 也可能返回空数组而不抛出异常。因此，判断一条数据流是否健康，至少要同时检查：

```text
连接状态
记录数量
最新闭合时间
最近补数时间
内部时间缺口
错误信息
```

## 17.14 一次真实运行说明了什么

系统首次持续运行后，部分查询结果如下：

```text
binance  1m   1007  2026-07-18 14:11:00  2026-07-19 06:57:00
binance  5m   1001  2026-07-15 19:30:00  2026-07-19 06:50:00
binance  1h   1000  2026-06-07 14:00:00  2026-07-19 05:00:00
okx     1m   1007  2026-07-18 14:11:00  2026-07-19 06:57:00
okx     5m   1001  2026-07-15 19:30:00  2026-07-19 06:50:00
okx     1h   1000  2026-06-07 14:00:00  2026-07-19 05:00:00
```

`1m` 从初始化的 1000 条增长到 1007 条，说明 WebSocket 正在持续写入。`5m` 增长到 1001 条，也符合周期闭合速度。`1h` 最新时间为 `05:00`，在查询时仍是正常闭合边界。

这组结果还体现了跨交易所比较的价值。两家交易所的记录数量和时间范围一致，说明周期计算、UTC 边界和持续写入基本协调。价格和成交量不要求完全相同，因为它们来自不同订单簿和不同参与者。

## 17.15 OKX 周线暴露的边界问题

同一次运行中，Binance 返回了 465 根周线，OKX 却没有周线记录。检查点显示 OKX WebSocket 为 `live`，`last_error` 为空，但 `last_closed_open_time` 仍然为空。

问题不在 WebSocket，而在初始 REST 起点。请求 1000 根周线相当于回溯约 19 年，早于 OKX BTC/USDT 的可用历史范围。Binance 对过早的 `since` 会从最早可用数据开始返回，OKX 在这种情况下可能直接返回空数组。

空数组不是网络异常，也不会自动产生报错。如果系统只检查 `status == live`，就会错误地认为周线数据已经准备完成。

这个案例给补数机制增加了三条要求：

```text
初始起点不能只用“当前时间减去目标数量”计算；
首次请求为空时，要区分“市场没有数据”和“起点早于可用历史”；
健康状态必须同时验证 last_closed_open_time 和记录数量。
```

更稳妥的实现可以读取市场创建时间作为参考，在首次空响应时尝试发现最早可用区间，并从第一个有效时间点向后分页。市场创建时间本身也可能不等于完整历史起点，因此最终仍要以实际返回数据为准。

这类差异说明：CCXT 统一了调用形式，却不能抹平交易所的全部行为。统一接口之后，仍然需要针对真实返回结果编写边界测试。

## 17.16 如何检查数据是否连续

采集器运行后，可以先按交易所和周期查看数量与时间范围：

```sql
SELECT
    exchange,
    timeframe,
    COUNT(*) AS row_count,
    MIN(open_time) AS first_candle,
    MAX(open_time) AS latest_candle
FROM market_candles
WHERE symbol = 'BTC/USDT'
GROUP BY exchange, timeframe
ORDER BY exchange, timeframe;
```

检查最近 24 小时的一分钟数据是否存在内部缺口：

```sql
WITH candle_gaps AS (
    SELECT
        exchange,
        open_time,
        TIMESTAMPDIFF(
            SECOND,
            LAG(open_time) OVER (
                PARTITION BY exchange
                ORDER BY open_time
            ),
            open_time
        ) AS gap_seconds
    FROM market_candles
    WHERE symbol = 'BTC/USDT'
      AND timeframe = '1m'
      AND open_time >= UTC_TIMESTAMP() - INTERVAL 1 DAY
)
SELECT *
FROM candle_gaps
WHERE gap_seconds > 60;
```

没有返回结果，表示这个时间范围内没有一分钟缺口。其他周期需要把阈值改成相应秒数。

除此之外，数据质量检查还应包括：

```text
唯一键是否重复
时间是否按周期递增
OHLC 是否满足价格关系
成交量是否为非负数
最新闭合时间是否符合当前周期
两家交易所价格是否出现异常偏离
接收时间与事件时间的延迟是否突然增大
```

## 17.17 逐笔成交比 K 线多了什么

逐笔成交记录撮合引擎已经完成的交易。一条统一成交数据通常包含：

```text
exchange
symbol
trade_id
timestamp
price
amount
side
received_at
```

成交方向通常表示主动成交方的方向，但不同交易所字段含义可能不同，不能只根据 `buy` 或 `sell` 推断市场整体意图。

逐笔成交可以用于计算主动买卖量、成交强度、大额成交和短期价格冲击。它也可以重新聚合为 K 线，用来交叉验证交易所提供的 OHLCV。

成交数据的补全方式与 K 线不同。公开 REST 往往只提供近期成交，分页可能按时间、成交 ID 或游标进行。断线时间过长后，早期逐笔成交可能已经无法从公开接口取回。因此，成交模块需要持久化 `trade_id` 或交易所序号，并明确记录可补历史窗口。

适合逐笔成交的唯一身份通常是：

```text
exchange + symbol + trade_id
```

如果交易所没有稳定成交 ID，只能组合时间、价格、数量和方向去重，但这种方式存在误判风险。

## 17.18 订单簿不是普通时间序列

订单簿由买盘 `bids` 和卖盘 `asks` 组成。L2 订单簿把相同价格的数量聚合到一个档位：

```text
bids：价格从高到低排列
asks：价格从低到高排列
```

第一档买价和第一档卖价之间的差称为点差。不同档位累计数量可以估算市场深度和大额订单的潜在滑点。

订单簿 WebSocket 通常不会每次推送完整状态，而是先提供快照，再持续推送增量。正确维护本地订单簿需要遵守类似流程：

```text
1. 建立 WebSocket，并暂存增量消息；
2. 通过 REST 获取订单簿快照；
3. 根据更新序号丢弃快照之前的增量；
4. 按顺序应用后续增量；
5. 数量变为零时删除对应价位；
6. 序号不连续或校验失败时，废弃本地状态并重新获取快照。
```

只要漏掉一个关键增量，本地订单簿就可能与交易所真实状态永久分叉。此时不能像 K 线一样简单地补一条缺失记录，而要重新取得完整快照。

## 17.19 为什么历史订单簿很难补齐

闭合 K 线是已经确定的时间聚合，交易所通常允许查询一段历史。订单簿是不断变化的状态，公开 REST 一般只能返回“现在”的快照。

如果系统在上午十点断线，下午一点重新连接，下午的快照可以恢复当前状态，却不能还原断线三小时内每一次挂单、撤单和队列变化。

因此，订单簿需要从一开始持续采集。需要历史微观结构研究时，通常有三种选择：

```text
自己长期保存快照和增量；
使用交易所提供的历史数据文件；
购买专业历史行情数据。
```

这也是“数据补全”必须按类型讨论的原因：

```text
K 线：通常可以通过 REST 恢复历史缺口；
成交：可以补近期记录，范围取决于交易所；
订单簿：可以恢复当前状态，通常无法恢复完整历史过程。
```

## 17.20 数据量决定存储方式

默认七个 K 线周期的数据量对 MySQL 压力有限。若加入一秒 K 线、逐笔成交和订单簿增量，数量会迅速上升。

一分钟 K 线一年约有 52.56 万条；一秒数据一年超过 3150 万条。逐笔成交和订单簿更新还会随市场活跃度变化，不能只按固定周期估算。

因此，当前存储策略分为两层：

```text
MySQL 热数据：近期闭合 K 线、唯一约束、采集进度和查询状态
Parquet 历史归档：后续保存按时间分区的大规模研究数据
```

订单簿当前状态更适合保存在进程内存或专门的低延迟状态层，研究快照和派生指标再按固定频率落盘。把每一次订单簿变化都同步写入普通业务表，可能让数据库成为采集瓶颈。

## 17.21 限流、断线和重试

交易所公开接口不等于无限调用。REST 和 WebSocket 都有连接数、订阅数和请求频率限制。

CCXT 的 `enableRateLimit=True` 可以降低连续请求过快的风险，但它不能替代业务层分页上限、失败重试和监控。补数页数必须有上限，避免配置错误导致无休止请求。

断线重连也不能使用固定的高频循环。当前采集器使用指数退避，并加入少量随机等待：

```text
1 秒 → 2 秒 → 4 秒 → 8 秒……直到最大等待时间
```

这样可以避免交易所故障时所有客户端同时快速重连。连接恢复前先执行 REST 对账，可以缩短数据空档。

稳定运行还需要服务器时钟同步。事件时间、接收时间和周期边界都依赖系统时间；服务器时钟偏差过大，会导致错误的“最新应闭合 K 线”判断。

## 17.22 公开行情也需要安全边界

Binance 和 OKX 的公开行情不需要 API Key。只读采集器没有必要加载交易权限，更不应该加载提现权限。

配置中仍要注意以下问题：

```text
不要把真实 API Key 和 Secret 提交到 GitHub；
不要在异常日志中输出请求签名或账户信息；
确认访问的是交易所官方域名；
了解服务器所在地区的服务可用性和交易所规则；
为外部返回内容设置大小、超时和字段校验；
交易所维护或协议变化时允许系统降级，而不是写入错误数据。
```

公开数据降低了账户风险，却没有消除数据供应风险。交易所可能维护、限流、更改字段、下架交易对或停止某个历史接口。多交易所对照、持久化检查点和明确错误状态，都是数据安全的一部分。

## 17.23 当前系统如何运行和观察

持续采集使用：

```bash
./scripts/run_collector.sh
```

只执行一次 REST 补数和缺口检查：

```bash
./scripts/run_collector.sh --once
```

日志中会出现补数进度和订阅状态。登录 Web 系统后，数据中心页面显示交易所、周期、记录数、最新闭合 K 线和状态；对应接口为：

```text
GET /api/v1/market/streams
```

页面状态适合日常观察，数据库查询适合判断时间范围和内部缺口，自动化测试负责确保解析、幂等写入和缺口恢复规则不会被后续修改破坏。三者不能相互替代。

## 17.24 当前完成范围与下一步

第一个 CEX 数据版本已经完成以下能力：

```text
Binance、OKX 现货 BTC/USDT
七种默认 K 线周期

只保存闭合 K 线

采集检查点、状态接口和数据中心展示
```

仍需继续完成的边界包括：

```text
OKX 等交易所在超早历史起点下的首条数据发现

```

把这些内容列为未完成项，不会削弱当前系统的价值。相反，它为后续开发提供了可以检查的完成标准，也避免读者把概念设计误认为已经验证过的代码。

## 17.25 本章小结

CEX 行情模块把第四章的一次性数据实验扩展成持续运行的数据服务。

K 线模块使用 WebSocket 接收新数据，使用 REST 初始化历史并修复缺口，使用统一 `Candle` 对象屏蔽交易所字段差异，再通过唯一键写入 MySQL。采集检查点记录连接、补数和异常状态，数据库查询与自动化测试继续检查记录数量、最新时间和内部连续性。

逐笔成交和订单簿则说明，不同数据类型不能套用同一种补数方法。成交历史受到公开接口窗口限制；订单簿可以恢复当前快照，却通常无法事后还原丢失的历史变化。

一套可靠的数据模块最终要回答四个问题：

```text
这条数据来自哪里？
它在什么时候真正可用？
中间是否缺失、重复或被修订？
发生异常后能够恢复到什么程度？
```

只有先回答这些问题，后续指标、策略和回测才有可信的输入。
