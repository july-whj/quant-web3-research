# 第十六章：开源系统的整体架构与目录设计

## 16.1 从一次实验走向一套系统

前十五章中的许多实验都可以在 Notebook 里完成。读取一份 BTC 行情，计算两条均线，生成买卖信号，再画出资金曲线，一个文件已经足以容纳完整过程。

Notebook 很适合学习。代码、文字、表格和图形出现在同一个页面里，读者可以逐段运行，也可以立即看到计算结果。但当实验逐渐增多，问题也会随之出现：同一段收益率代码被复制到不同文件，手续费参数散落在多个单元格中，数据保存位置不一致，修改一次策略规则后，不知道哪些结果需要重新计算。

这时，项目面对的已经不是“如何再写一个 Notebook”，而是另一类问题：

```text
数据从哪里进入系统？
策略规则保存在哪里？
回测由谁执行？
结果如何复现？
异常由谁记录？
哪些代码可以被书稿、Notebook、接口和命令行共同使用？
```

开源量化项目的价值，不在于文件数量多，而在于研究过程能够被重复执行、检查和修改。一个读者拿到仓库后，应当可以从公开数据开始，按照明确步骤得到策略信号、回测结果和风险指标，而不是只能看到作者电脑上已经生成的一张收益曲线。

因此，从第十六章开始，研究对象由单个知识点转向完整系统。书稿不再先设想功能，再寻找代码示例；章节内容直接来自系统中已经存在的模块、配置、测试和运行结果。

## 16.2 系统要解决什么问题

Quant Web3 Research 的目标，是形成一条可复现的研究链路：

```text
公开行情与链上数据
        ↓
采集、校验与标准化
        ↓
指标与策略信号
        ↓
回测与交易成本
        ↓
收益、回撤和风险指标
        ↓
报告、图表与实验记录
```

这条链路强调“研究”，而不是“自动赚钱”。首版系统有清晰的边界：

- 读取公开行情和公开链上数据；
- 运行历史回测和模拟实验；
- 保存参数、结果和数据来源；
- 展示研究过程和风险指标；
- 不保存钱包私钥或助记词；
- 不默认连接真实账户下单；
- 不根据回测结果承诺未来收益。

边界不是功能不足的借口，而是系统设计的一部分。量化研究、模拟交易和真实资金执行所承担的风险完全不同。把它们拆成不同阶段，可以让数据问题、策略问题和执行问题分别暴露，而不是在真实资金发生损失后才开始排查。

## 16.3 五个独立运行单元

当前系统由五个主要运行单元组成：

```text
React Web ──HTTP / Cookie──> FastAPI ──SQL──> MySQL 8.x
                                │
                                ├──Queue──> Redis / RQ Worker
                                │                 │
                                └─────────────> quant_web3 核心包
                                                  │
                                                  └──> 回测产物

Binance / OKX ──WebSocket──> Collector ──幂等写入──> MySQL
       └──────────REST 补数与缺口修复───────────────┘
```

五个运行单元分别是：

| 运行单元 | 主要职责 | 不承担的职责 |
|---|---|---|
| Web | 登录、参数输入、状态与结果展示 | 保存私钥、执行核心回测 |
| API | 身份验证、研究接口、任务提交 | 长时间占用请求线程采集行情 |
| Worker | 执行耗时回测任务 | 对外提供网页 |
| Collector | 订阅行情、补齐缺口、记录采集状态 | 生成策略信号和真实下单 |
| MySQL / Redis | 持久化状态、保存热数据、分发任务 | 判断策略是否值得交易 |

这些单元可以运行在同一台开发电脑上，也可以在部署时分开。拆分的目的不是追求复杂，而是防止一个环节的故障扩散到整个系统。

例如，交易所 WebSocket 断线时，Collector 可以独立重连，API 仍然能够响应用户请求；一次回测运行时间较长时，Worker 可以继续计算，Web 页面只需要查询任务状态；前端界面发生变化时，数据采集逻辑不需要跟着重写。

## 16.4 为什么行情采集器必须独立

把行情订阅写在 FastAPI 的某个接口里，看起来更简单：用户访问页面时建立连接，收到数据后写入数据库。但这种做法会把两个生命周期完全不同的任务绑在一起。

HTTP 请求通常在几毫秒到几秒内完成，WebSocket 行情连接却要持续运行数小时甚至数天。API 服务还可能因为发布新版本、增加进程或健康检查而重启。如果行情采集依附于某个请求或某个 Web 进程，就容易出现重复订阅、连接中断和数据空档。

独立 Collector 具有自己的运行循环：

```text
启动
→ 建立采集检查点
→ REST 补齐已有缺口
→ 建立 WebSocket 订阅
→ 持续接收闭合 K 线
→ 定时检查缺口
→ 断线后补数并重新连接
```

这个进程只关心行情是否连续、数据是否有效以及写入是否成功。策略研究通过数据库读取已经整理好的数据，不需要知道某条 K 线究竟来自 WebSocket 还是 REST。

## 16.5 项目目录不是文件分类表

目录设计的核心是职责边界。当前仓库的主要结构如下：

```text
quant-web3-research/
├── apps/
│   ├── api/                 # FastAPI 接口与数据库模型
│   ├── collector/           # Binance、OKX 行情采集与补数
│   ├── web/                 # React 研究工作区
│   └── worker/              # Redis / RQ 后台任务
├── src/quant_web3/
│   ├── backtest/            # 回测引擎
│   ├── chain/               # 链上 RPC 读取
│   ├── data/                # 可复用的数据访问函数
│   ├── indicators/          # 技术指标
│   ├── risk/                # 收益与风险指标
│   └── strategies/          # 策略规则
├── configs/                 # 数据、策略与回测参数
├── data/
│   ├── raw/                 # 原始数据
│   ├── processed/           # 标准化数据
│   └── reports/             # 回测和研究产物
├── docs/                    # 书稿、架构和研究说明
├── examples/                # 可直接运行的最小示例
├── notebooks/               # 按章节组织的交互实验
├── tests/                   # 自动化测试
├── infra/                   # MySQL、Redis 与容器编排
├── scripts/                 # 常用启动与维护命令
├── .env.example             # 环境变量模板
├── pyproject.toml           # Python 项目与依赖定义
└── README.md                # 项目入口
```

如果只按文件类型划分目录，所有 Python 文件都可以放进一个 `python/` 文件夹，所有 Markdown 都可以放进一个 `markdown/` 文件夹。但这样的目录无法表达代码在系统中承担什么职责。

按照模块划分后，路径本身就能提供信息：`apps/collector/` 表示它是一个可以独立运行的应用，`src/quant_web3/risk/` 表示其中是可复用的风险计算，`tests/collector/` 表示这些测试专门验证采集链路。

## 16.6 `apps` 和 `src` 的区别

`apps/` 保存可以独立启动的应用，`src/quant_web3/` 保存不依赖具体界面的研究能力。

以最大回撤为例，它既可能在 Notebook 中被调用，也可能用于命令行回测、Worker 后台任务或 API 返回结果。因此，最大回撤不应写在某个页面或路由里，而应放在 `src/quant_web3/risk/` 中。

相反，钱包登录路由只属于 Web 服务，行情 WebSocket 重连只属于 Collector。它们需要数据库连接、运行状态和外部协议，放在 `apps/` 更符合实际职责。

可以用一个简单问题判断代码应该放在哪里：

```text
这段代码离开当前应用后，是否仍然是一个完整、可复用的研究能力？
```

如果答案是肯定的，它更适合进入 `src/quant_web3/`；如果它负责启动服务、处理请求、连接外部系统或管理进程生命周期，它通常属于 `apps/`。

## 16.7 Web 前端负责表达，不负责保管密钥

`apps/web/` 使用 React、TypeScript、Vite 和 Tailwind CSS。页面按照研究流程组织，包括首页、钱包登录、数据中心、策略实验室和回测任务。

前端还提供简体中文、繁体中文、日文和英文四种界面语言。语言切换属于表达层功能，不应改变数据库中的行情时间、策略参数或计算结果。同一份回测结果可以用不同语言展示，但数值含义必须一致。

钱包登录通过签名证明用户控制某个地址。签名过程不需要把私钥交给网站，系统也不应要求用户输入助记词。浏览器只把签名结果发送给服务端，服务端验证地址后建立会话。

因此，前端的安全边界十分明确：

```text
可以请求钱包签名；
不能读取或保存钱包私钥；
可以展示交易所公开数据；
不能把交易所 Secret 写入浏览器代码；
可以提交研究参数；
不能把前端计算结果当作唯一可信记录。
```

## 16.8 API、Worker 与核心研究代码

FastAPI 负责系统对外接口。登录挑战、会话、数据状态和回测任务都通过明确的路由暴露。路由只处理输入、权限和输出，不重复实现收益率、均线或回撤公式。

耗时任务由 Worker 执行。开发阶段的小规模回测可以同步运行，部署环境则通过 Redis 和 RQ 把任务交给独立进程。这样，浏览器不需要保持一个长时间等待的 HTTP 请求，API 也不会因为一次大规模回测停止响应。

真正的研究计算仍然来自 `src/quant_web3/`。这种安排让四种使用方式共享同一套规则：

```text
书稿中的代码说明
Notebook 中的交互实验
examples 中的命令行程序
Web 系统中的回测任务
```

如果四个入口各自实现一套计算，项目很快会出现“书里一种结果、页面另一种结果”的问题。共享核心模块，是可复现研究的基础。

## 16.9 数据存储为什么不只选一种工具

不同数据具有不同访问方式。把所有内容塞进同一种存储，并不会自动让系统变简单。

MySQL 8.x 保存需要即时查询、关联和约束的数据，例如用户、钱包、会话、采集检查点、近期闭合 K 线、回测状态、参数和摘要。行情表可以通过唯一键避免重复记录，也可以按交易所、交易对、周期和时间查询。

Redis 用于任务队列和短期状态。它适合快速传递任务，但不作为用户会话、行情或回测结果的唯一持久化来源。

Parquet 适合保存规模较大的时间序列和回测产物。列式存储可以让 Pandas 和分析工具高效读取指定字段。当前系统先把实时闭合 K 线写入 MySQL 热数据层，后续再按时间分区归档历史数据。

三者的关系可以概括为：

```text
MySQL：可查询、可约束的系统事实
Redis：可以重新生成的队列和短期状态
Parquet：面向分析的大规模时间序列产物
```

## 16.10 配置、代码与密钥必须分开

策略参数不应该散落在代码里，连接地址和密钥也不应该写死在仓库中。

项目使用三类配置：

| 配置类型 | 示例 | 保存位置 |
|---|---|---|
| 可公开的研究参数 | MA20、MA60、初始资金 | `configs/` |
| 可公开的配置模板 | 数据库变量名、采集周期 | `.env.example` |
| 本机或服务器秘密 | 数据库密码、API Secret | `.env` 或密钥服务 |

`.env.example` 只提供变量名和安全占位值，帮助读者理解系统需要哪些配置。真正的 `.env` 被 `.gitignore` 排除，不能提交到 GitHub。

即使交易所 API Key 只开放读取权限，也不应该出现在书稿、Notebook 输出、截图、日志或报错信息中。未来接入交易权限时，还需要进一步限制提现权限、来源 IP、账户额度和密钥可见范围。

## 16.11 `docs`、`notebooks`、`examples` 和 `tests` 的关系

这四个目录分别回答不同问题。

`docs/` 解释概念、设计选择、限制和结论。书稿中的代码可以适当简化，但不能描述一个实际上不存在的系统能力。

`notebooks/` 保存学习过程和可视化实验。它允许逐段运行，但不作为生产服务的入口。

`examples/` 提供最小可执行程序。`examples/backtest_ma_cross.py` 展示如何从命令行完成一次双均线回测，`examples/fetch_cex_ohlcv.py` 展示如何读取公开 K 线。

`tests/` 把关键假设变成自动检查。例如，资金曲线是否避免未来函数、行情写入是否幂等、缺失的中间 K 线能否被发现、交易所消息能否正确转换为统一字段。

它们之间形成一条验证关系：

```text
书稿说明为什么这样设计
Notebook 展示计算过程
Example 提供最小运行入口
Test 证明关键规则没有被后续修改破坏
```

## 16.12 从一条功能看目录如何协作

以 BTC/USDT 行情采集为例，一项功能会同时经过多个目录：

```text
.env.example
    定义交易所、交易对、周期和巡检间隔

apps/collector/
    建立 WebSocket、执行 REST 补数、检查缺口

apps/api/app/models/
    定义行情表和采集检查点

apps/api/app/api/routes/
    提供采集状态查询接口

apps/web/src/pages/
    在数据中心展示记录数和最新闭合时间

tests/collector/ 与 tests/api/
    验证解析、幂等写入、缺口恢复和接口结果

docs/03-system-practice/
    把实现过程整理成第十七章
```

这正是“内容从系统中来”的含义。书稿不是代码完成后的宣传材料，而是对设计选择、验证结果和已知限制的完整记录。

## 16.13 最小启动流程

项目根目录使用虚拟路径表示为 `quant-web3-research/`。本地启动流程如下：

```bash
cd quant-web3-research

python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e ".[dev]"

cp .env.example .env
docker compose -f infra/docker-compose.yml up -d mysql redis
python scripts/init_db.py
```

API、Collector 和 Web 分别运行：

```bash
./scripts/run_api.sh
./scripts/run_collector.sh

cd apps/web
npm install
npm run dev
```

当 `JOB_MODE=rq` 时，还需要启动后台任务：

```bash
./scripts/run_worker.sh
```

每个进程独立启动，使故障位置更容易判断。API 无法连接数据库、Collector 无法订阅交易所、Worker 无法连接 Redis，是三类不同问题，不应该被一个笼统的“系统启动失败”掩盖。

## 16.14 开源项目还需要工程边界

能够运行的代码不等于完整的开源项目。公开仓库还需要向使用者说明以下内容：

```text
README：项目是什么，如何开始运行
LICENSE：代码可以如何使用和再分发
CONTRIBUTING：如何提交问题和代码
SECURITY：如何报告安全问题，哪些信息不能公开
DISCLAIMER：研究结果不构成收益承诺或投资建议
```

这些文件不是形式工作。量化和 Web3 项目同时接触资金、钱包、交易所和外部数据，如果不写明安全边界，读者很容易把研究工具误解为可以直接托管资产的交易产品。

开源也不意味着必须公开所有运行秘密。代码、接口规范、数据结构和测试可以公开，服务器密码、钱包私钥、交易所 Secret、内部监控地址和真实用户数据必须留在受控环境中。

## 16.15 架构不是一次性设计

系统架构会随着研究目标变化。首版只采集 BTC/USDT 闭合 K 线，MySQL 足以承担热数据查询；当交易对、秒级数据和订单簿数量增加后，存储分区、消息缓冲、归档和监控都需要重新评估。

这并不意味着首版设计错误。合理的架构应当满足当前目标，同时为下一阶段保留清晰的扩展位置。没有实际数据量时就引入大量中间件，只会增加维护成本；完全不考虑模块边界，则会让每次扩展都变成重写。

当前目录已经为后续章节留下位置：

```text
第 17 章：apps/collector 与 src/quant_web3/data
第 18 章：src/quant_web3/chain
第 19 章：src/quant_web3/indicators 与 utils
第 20 章：src/quant_web3/strategies 与 configs/strategies
第 21 章：src/quant_web3/backtest 与 reporting
第 22 章：paper_trading 与 risk
第 23 章：监控、部署和复盘记录
```

## 16.16 本章小结

量化研究从 Notebook 走向系统，并不是把代码移动到更多文件夹，而是建立稳定的职责边界。

当前开源系统把界面、接口、后台任务、行情采集和研究核心拆成独立模块；把系统状态、短期队列和分析产物放进适合的存储；把公开配置模板与真实秘密分离；再用文档、示例和测试共同维护研究过程。

目录结构最终要回答的不是“文件放得是否整齐”，而是三个更重要的问题：

```text
一项研究结果能否被重新运行？
一处规则修改会影响哪些模块？
一次故障能否被快速定位并恢复？
```

第十七章进入系统的第一个持续运行模块：CEX 行情采集。它不只处理“如何获取一份 K 线”，还要处理实时订阅、历史补数、重复消息、时间缺口和交易所差异。
