# 系统架构：从学习代码到开源研究系统

## 1. 设计目标

Quant Web3 Research 的首要目标，是把行情获取、策略定义、回测和风险评估组成一条可以重复执行的研究链路。系统默认不接入真实账户下单，不在服务端保存私钥，也不把回测收益包装成投资承诺。

首版由四个运行单元组成：

```text
React Web ──HTTP/Cookie──> FastAPI ──SQL──> MySQL 8.x
                              │
                              ├──Queue──> Redis/RQ Worker
                              │                │
                              └────────────> quant_web3 核心包
                                               │
                                               └──> Parquet 回测产物
```

## 2. 前端边界

`apps/web` 使用 React、TypeScript、Vite 和 Tailwind CSS。前端负责钱包连接、研究参数编辑、任务状态与结果可视化，不在浏览器内保存私钥或交易所 Secret。

页面按研究流程组织：

- 首页：解释“可复现研究”而不是宣传收益；
- 钱包登录：连接 EVM 钱包并签署一次性消息；
- 数据中心：管理数据来源和版本；
- 策略实验室：说明策略规则、参数与成本假设；
- 回测任务：提交任务、轮询状态并展示核心指标。

视觉规则参考 Kraken 的设计约束，但仅复用颜色层级、间距、边框和状态表达原则，继续使用本项目自己的名称、Logo 和信息架构。

## 3. 服务端边界

`apps/api` 是 FastAPI 应用。路由分为登录、策略、数据集、回测和统计五组。业务计算不直接写在路由中，而是复用 `src/quant_web3`，确保书稿、Notebook、命令行示例与 Web 系统使用同一套计算规则。

`apps/worker` 是 RQ 任务进程。开发环境可以设置 `JOB_MODE=inline`，在 API 进程内同步完成小规模演示；部署环境使用 `JOB_MODE=rq`，由 Redis 分发任务，避免长时间回测阻塞 HTTP 请求。

## 4. 数据存储

MySQL 8.x 只保存需要查询和关联的元数据：用户、钱包、登录挑战、会话、数据集索引、回测状态、参数和摘要。完整 K 线、净值序列和逐笔结果保存为 Parquet 文件，避免把大体量时间序列塞进关系数据库。

Redis 只承担队列和短期缓存，不作为用户、会话或回测结果的唯一数据源。

## 5. 钱包登录

登录消息由服务端生成，包含域名、URI、Chain ID、随机 Nonce、签发时间与过期时间，结构遵循 EIP-4361。浏览器请求钱包签署文本消息，服务端恢复签名地址并与挑战记录核对。

安全约束包括：

- Nonce 只允许使用一次，默认五分钟过期；
- 验证成功后只把随机会话令牌写入 HttpOnly Cookie；
- 数据库只保存会话令牌的 SHA-256 摘要；
- 首版只支持 EOA 钱包，智能合约钱包需要后续加入 EIP-1271；
- 签名登录不产生链上交易，也不包含资产授权内容。

用户统计使用登录事件聚合，只暴露给带有 `X-Admin-Key` 的管理接口。IP 地址不以明文保存。

## 6. 后续演进

V0.1 先完成登录、数据登记、双均线回测和结果展示。V0.2 再加入真实数据集版本、策略代码版本、参数对比和实验报告。模拟交易、交易所只读 API、风险告警与实盘执行必须作为独立阶段推进，并在进入下一阶段前补充权限隔离、密钥管理和熔断机制。
