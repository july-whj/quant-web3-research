# 第十四章：智能合约、RPC、节点与区块浏览器

前面几章讲了账户、交易、Gas 和 Token。

接下来要回答一个更实际的问题：程序如何读取链上数据？

Web3 量化研究不一定要马上写智能合约，但一定会读取智能合约产生的数据。

例如：

```text
读取 ERC-20 转账
读取 DEX 交易事件
读取资金池储备
读取某个地址余额
读取交易回执
读取区块高度和时间
```

这些动作背后，都会涉及智能合约、节点、RPC、事件日志和区块浏览器。

## 14.1 智能合约是什么

智能合约是部署在链上的程序。

它有自己的地址、代码和状态。

用户可以向合约发起交易，调用合约中的方法。合约按照代码执行，执行结果写入链上状态。

常见智能合约包括：

```text
ERC-20 Token 合约
DEX 路由合约
流动性池合约
借贷协议合约
NFT 合约
跨链桥合约
预言机合约
多签钱包合约
```

从交易者视角看，合约是链上市场规则的载体。

Token 为什么能转账，DEX 为什么能兑换，资金池为什么能记录储备，授权为什么能让合约使用用户 Token，都是因为合约代码定义了规则。

## 14.2 合约地址不等于普通地址

合约也有地址。

但合约地址和普通用户地址不同。

普通外部账户由私钥控制。合约账户由代码控制。

你可以向合约地址发起交易，但合约如何响应，取决于它的代码。

区块浏览器里看到某笔交易的 `to` 是合约地址时，不要简单理解为“转账给某个人”。它可能是在调用一个合约方法。

例如：

```text
to 是 USDT 合约：可能是 Token 转账或授权。
to 是 DEX Router：可能是兑换。
to 是资金池合约：可能是 swap、mint、burn。
to 是跨链桥合约：可能是锁仓或跨链消息。
```

分析链上行为时，合约地址的语义很重要。

## 14.3 只读调用和写入交易

和合约交互时，要区分只读调用和写入交易。

只读调用不会改变链上状态。

例如：

```text
查询 Token 名称
查询 decimals
查询某个地址余额
查询资金池储备
查询当前授权额度
```

只读调用通常不需要用户签名，也不需要支付 Gas。

写入交易会改变链上状态。

例如：

```text
转账
授权
兑换 Token
添加流动性
移除流动性
部署合约
```

写入交易需要签名，通常需要支付 Gas，并产生交易哈希。

做数据分析时，只读调用可以作为安全起点。涉及写入交易，就进入执行和安全领域。

## 14.4 ABI 是什么

ABI 是合约对外接口的说明。

它告诉外部程序：

```text
合约有哪些方法
方法需要哪些参数
方法返回什么结果
有哪些事件
事件字段是什么
```

没有 ABI，链上数据仍然存在，但人和程序很难理解调用内容。

区块浏览器中的 Read Contract 和 Write Contract 页面，就是根据 ABI 把合约方法展示出来。

Python 程序读取合约时，也需要 ABI。

例如要读取 ERC-20 的 `balanceOf`，程序需要知道这个方法的名称、参数和返回值。

## 14.5 input data 和函数选择器

合约交易中经常会看到 `input data`。

这是一段编码后的调用数据。

在 EVM 合约中，`input data` 开头部分通常包含函数选择器，用来表示调用哪个方法。后面部分是编码后的参数。

用户在钱包中看到的是“兑换 100 USDC 为 ETH”，链上记录中可能表现为一段很长的十六进制数据。

区块浏览器如果有 ABI，就能把这段数据解码成更容易理解的函数调用。

如果合约未验证，或者没有 ABI，分析难度会明显增加。

对量化研究来说，不能只看交易成功与否，还要理解这笔交易到底调用了什么方法。

## 14.6 事件日志是什么

智能合约执行过程中，可以发出事件日志。

事件日志很适合外部系统索引。

ERC-20 的 `Transfer` 事件通常记录：

```text
from
to
value
```

DEX 的 `Swap` 事件可能记录：

```text
交易发起方
输入资产数量
输出资产数量
接收方
池子地址
```

链上数据分析经常不是逐个查询地址余额，而是扫描事件日志，再按地址、Token、时间、池子聚合。

例如要统计某个 Token 的大额转账，通常会扫描该 Token 合约的 `Transfer` 事件。

要统计某个 DEX 池子的成交量，通常会扫描池子合约的 `Swap` 事件。

事件日志是链上量化数据的核心来源之一。

## 14.7 节点是什么

节点是运行区块链客户端的软件和机器。

节点负责接收区块、验证交易、维护链上状态，并向外提供数据。

不同类型节点能力不同。

常见类型包括：

```text
全节点
归档节点
轻节点
第三方节点服务
```

全节点保存当前状态和必要历史数据，能验证链。

归档节点保存更完整的历史状态，适合查询很久以前某个区块高度的状态，但运行成本高。

第三方节点服务提供现成 RPC，使用方便，但有速率限制、可用性、延迟和信任边界。

对量化研究来说，节点质量会影响数据质量。

RPC 节点不同步、限流、延迟或返回错误，都可能让程序漏数据、重复数据或扫描中断。

## 14.8 RPC 是什么

RPC 是程序和节点通信的接口。

当 Python 程序要读取链上数据时，通常不会自己运行完整节点，而是向某个 RPC 节点发送请求。

常见 JSON-RPC 请求包括：

```text
获取最新区块高度
获取某个区块
获取某笔交易
获取交易回执
查询地址余额
调用合约只读方法
查询事件日志
估算 Gas
广播已签名交易
```

可以把关系写成：

```text
Python 程序
→ RPC 请求
→ 节点
→ 链上数据
```

后续使用 `web3.py` 时，背后就是这条路径。

## 14.9 区块浏览器是什么

区块浏览器是把链上数据整理成人类可读页面的工具。

它通常提供：

```text
地址页面
交易页面
区块页面
合约页面
Token 页面
事件日志
图表和统计
API
```

区块浏览器很方便，但它不是链本身。

区块浏览器的数据来自节点、索引系统和解析逻辑。不同浏览器可能存在同步延迟、解析差异或标签差异。

学习阶段可以用区块浏览器理解字段。

进入程序化研究后，要知道底层数据来自区块、交易、回执、日志和状态。

## 14.10 直接 RPC 和索引服务

读取链上数据通常有两条路径。

第一条是直接 RPC：

```text
Python → RPC → 节点 → 区块 / 交易 / 日志
```

优点是更接近原始数据。

缺点是需要处理分页、重试、区块范围、速率限制、重组、日志解析和异常恢复。

第二条是使用索引服务：

```text
Python → 索引 API → 已整理数据
```

优点是方便，适合快速研究。

缺点是要理解索引规则、延迟、覆盖范围和字段定义。

索引服务返回的数据不应被当作天然正确。关键研究结论最好能抽样回到链上原始数据校验。

## 14.11 交易回执为什么重要

一笔交易上链后，除了交易本身，还会有交易回执。

交易回执包含执行结果。

常见信息包括：

```text
status
gasUsed
logs
contractAddress
blockNumber
transactionHash
```

交易对象告诉我们“用户提交了什么请求”。

交易回执告诉我们“这笔请求执行后的结果”。

如果只看交易，不看回执，就很难判断交易是否成功，也看不到事件日志。

后续做链上数据分析时，交易回执会是核心数据来源。

## 14.12 和量化研究的关系

链上量化不是简单调用一个 API。

同样一笔 DEX 交易，可能需要同时读取：

```text
交易本身
交易回执
事件日志
Token decimals
池子合约信息
区块时间
Gas 成本
交易路径
```

如果只读取交易哈希和金额，结论很容易错。

例如，要计算某个池子的真实成交量，需要解析 Swap 事件，还要处理 Token 精度、交易方向、池子地址和多跳路径。

这就是为什么本书先讲合约、RPC、节点和区块浏览器，再进入链上数据实践。

## 本章实践

找一个 ERC-20 Token 合约页面，记录：

```text
所在链：
合约地址：
是否已验证源码：
Read Contract 中能查询哪些信息：
Write Contract 中有哪些高风险方法：
是否能看到 Transfer 事件：
是否能看到交易回执中的 logs：
Token decimals 是多少：
区块浏览器是否标记为官方合约：
```

再找一笔该 Token 的转账交易，记录：

```text
交易哈希：
交易状态：
from：
to：
交易调用的合约：
事件日志中的 from：
事件日志中的 to：
Gas Used：
```

比较交易字段里的 `to` 和事件日志里的 `to` 是否相同。

## 本章小结

智能合约是链上的程序。只读调用用于查询状态，写入交易会改变状态并消耗 Gas。

ABI 帮助外部程序理解合约方法和事件。RPC 是程序访问节点的入口。节点提供链上数据。区块浏览器是展示和索引工具，不是链本身。

链上量化研究的核心数据通常来自交易、回执和事件日志。读取数据不难，正确解释数据才是难点。
