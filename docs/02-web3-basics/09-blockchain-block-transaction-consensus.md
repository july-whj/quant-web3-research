# 第九章：区块链、区块、交易与共识

学习 Web3 量化交易，不能只看交易所价格。

交易所 K 线告诉我们价格如何变化。链上数据告诉我们资产如何转移、地址如何交互、合约如何被调用、资金池如何变化。

如果只看 K 线，Web3 和普通金融市场的差别并不明显。一旦进入链上数据，交易者就会遇到新的问题：区块高度、交易哈希、Gas、事件日志、确认数、区块重组、最终性。

这些概念不是技术装饰。它们会影响数据是否可靠、信号是否及时、交易是否已经完成，以及回测能否接近真实执行。

本章先建立基础语言：区块链、区块、交易和共识。

## 9.1 “账本”是入门比喻，不是完整定义

很多教材会说，区块链是一份公开账本。

这个说法适合入门，但不能停在这里。

账本这个比喻能说明两点：

```text
链上记录按顺序追加。
历史记录可以被公开检查。
```

但不同区块链记录的内容并不完全一样。

比特币更接近一套 UTXO 账本。它关心的是哪些未花费输出还存在，以及这些输出如何被新的交易消耗。

以太坊更接近一台分布式状态机。它不只记录转账，还记录账户余额、合约代码、合约存储、事件日志和每次交易后的状态变化。

所以，更准确的理解是：

```text
区块链是一套由节点共同维护的、有顺序的、可验证的状态记录系统。
```

这句话比“公共账本”复杂一点，但更接近后续链上数据分析需要面对的现实。

对本书来说，不需要马上掌握所有底层数据结构。先记住三个点：

- 区块链记录的不是单纯价格，而是交易和状态变化。
- 这些记录按区块顺序组织。
- 节点通过共识机制决定哪一段历史是被网络接受的历史。

## 9.2 区块是什么

区块可以理解为一批交易和相关验证信息的集合。

如果把区块链看作一条时间线，区块就是时间线上的一个个节点。每个新区块都会引用前一个区块，使得区块之间形成连续结构。

一个区块通常包含这些信息：

```text
区块高度或区块编号
区块哈希
父区块哈希
区块时间
交易列表
状态根或交易根
Gas 使用情况
出块者或验证者信息
```

不同链的字段名称和结构会有差异。比特币区块、以太坊区块、Solana 区块并不完全一样。这里先用通用视角理解。

区块高度表示区块在链上的位置。高度越大，通常说明区块越靠近当前时间。

区块哈希可以理解为区块内容的指纹。区块内容改变，哈希也会改变。

父区块哈希负责连接前后区块。新区块引用旧区块，旧区块又引用更早的区块，链式结构由此形成。

区块时间是链上记录的时间。做数据分析时，区块时间很重要，但它不是传统交易所里的逐笔成交时间。区块时间来自链的出块过程，不同链的时间精度和稳定性不同。

以太坊现在使用权益证明机制，时间被划分为 slot。理论上每 12 秒一个 slot，但并不是每个 slot 都一定产生区块。比特币的出块时间更随机，协议目标是平均约 10 分钟一个区块。

这意味着，链上时间不是完全均匀的时间序列。后续把链上数据转换成分钟线、小时线或日线时，要注意时间聚合方式。

## 9.3 区块为什么要引用上一个区块

区块引用上一个区块，是为了让历史记录形成顺序。

如果某个历史区块被修改，它的哈希会改变。后面引用它的区块也会受到影响，后续区块的连接关系会被破坏。

这并不表示历史绝对不可改变。更准确的说法是：修改已经被网络接受的历史，需要付出极高成本，并且越早的历史越难被改动。

在 PoW 链上，攻击者需要重新计算大量工作量，并超过诚实网络接受的链。

在 PoS 链上，攻击者需要控制大量质押权重，并可能面临惩罚和罚没。

因此，区块链的安全性不是来自“没人能改数据库”这样一句话，而是来自密码学、网络传播、经济激励和共识规则的组合。

对量化研究来说，理解到这一层就够用：越新的区块越不稳定，越旧的区块越稳定。策略使用链上数据时，必须考虑这个稳定性差异。

## 9.4 交易是什么

交易是经过签名的状态变更请求。

这句话比“转账”更准确。

最简单的交易是从一个地址向另一个地址转出原生资产，例如转 ETH。

但在智能合约链上，交易还可以做更多事情：

```text
调用 Token 合约完成转账
授权某个合约使用自己的 Token
调用 DEX 路由合约兑换资产
向资金池添加或移除流动性
部署一个新合约
参与借贷、质押或清算
```

以太坊中，一笔交易通常由外部账户发起，也就是由私钥控制的钱包地址发起。合约账户不会像人一样主动发起一笔外部交易，但合约在被调用后，可以在同一笔交易执行过程中调用其他合约。

这个区别很重要。

当区块浏览器上看到 `from`、`to` 和合约调用时，不能简单理解为“某个合约主动发起了操作”。很多时候，是某个钱包地址发起交易，交易调用了一个合约，合约又触发了后续内部调用和事件日志。

## 9.5 一笔交易里有哪些关键字段

不同链的交易字段不同。以 EVM 链为例，一笔交易常见字段包括：

| 字段 | 含义 |
|---|---|
| transaction hash | 交易哈希，一笔交易的唯一标识 |
| from | 发起交易的地址 |
| to | 接收地址或被调用的合约地址 |
| value | 原生资产转账数量 |
| input data | 调用合约时携带的数据 |
| nonce | 发起地址的交易序号 |
| gas limit | 这笔交易最多愿意消耗多少 Gas |
| gas used | 实际消耗的 Gas |
| gas price / fee fields | Gas 单价或费用相关字段 |
| status | 成功或失败 |
| block number | 交易被打包进哪个区块 |
| timestamp | 所在区块的时间 |

这些字段中，初学者最容易忽略的是 `input data`、`nonce` 和 `status`。

`input data` 决定了这笔交易到底在调用什么合约方法。普通转账可能没有复杂输入数据，但 DEX 交易、授权、合约调用都会有。

`nonce` 用来标识同一个地址发出的交易顺序。一个地址连续发多笔交易时，nonce 会影响交易执行顺序。

`status` 表示交易是否成功。链上能查到交易，不代表交易成功。失败交易也可能被打包进区块，并消耗 Gas。

对 Web3 量化交易来说，不能只统计交易数量，还要区分成功交易、失败交易、转账交易、授权交易和真实兑换交易。

## 9.6 交易从发出到上链的过程

一笔交易不会在签名后立刻成为链上历史。

在以太坊这类链上，简化流程可以写成：

```text
用户在钱包中构造交易
用户用私钥签名
交易被发送到节点
节点检查交易格式、签名、余额和费用
有效交易进入节点的待处理交易集合
交易在网络中传播
出块者或验证者选择交易打包
交易被执行
新区块被广播
其他节点验证区块和状态变化
交易获得确认
```

这里有两个细节。

第一，待处理交易集合并不是一个全网完全一致的“公共池子”。不同节点看到的待处理交易可能不同，传播速度也不同。

第二，交易进入待处理状态，不代表一定会被打包。Gas 费用太低、nonce 冲突、余额变化、网络拥堵、交易被替换，都可能导致交易长时间 pending 或最终不再被执行。

这对链上策略很关键。

如果策略监控 pending 交易，就要处理大量不确定性。如果策略只使用已经上链的数据，就会更稳定，但信号会更滞后。

## 9.7 确认数、最终性和区块重组

交易被打包进区块后，通常会显示确认数。

可以先这样理解：

```text
确认数 = 当前最新区块高度 - 交易所在区块高度 + 1
```

确认数越多，说明这笔交易后面已经接上了更多新区块。它被回滚的概率通常越低。

但“确认”和“最终性”不是完全相同的概念。

确认数是一种观察方式。它描述交易所在区块之后又增加了多少区块。

最终性描述的是交易所在区块是否已经达到协议层面很难被改变的状态。

在 PoW 链上，最终性更偏概率意义。区块越深，被重组的概率越低，但理论上仍可能被更长有效链替代。

在以太坊 PoS 中，最终性和验证者投票、检查点有关。当区块进入 finalized 状态后，要回滚它需要极高经济代价。

区块重组指的是节点最终接受了另一条区块分支，导致原来某些较新的区块不再属于主链。

对普通用户来说，小规模重组不常被感知。对链上数据系统来说，它必须被处理。

如果你的程序刚扫描到一笔交易，马上写入数据库并当成不可变事实，之后发生重组，就可能出现错误记录。

所以，链上数据系统常见做法是：

```text
最新区块先暂存
等待若干确认后再标记为稳定
发现重组时回滚受影响区块
对交易和事件日志做幂等处理
```

本书后续做入门实验时，不会马上实现完整重组处理。但从概念上要知道：链上数据不是一出现就绝对稳定。

## 9.8 共识机制解决什么问题

区块链网络由许多节点组成。节点可能在不同时间收到不同交易，也可能短时间内看到不同候选区块。

共识机制要解决的问题是：这些节点如何对同一份链上历史和当前状态达成一致。

常见说法会把共识机制简化成 PoW、PoS、PoA。这个说法方便，但不完整。

更准确地说，PoW、PoS、PoA 是共识机制中的核心组成部分。完整共识还包括区块提议、区块验证、分叉选择、奖励惩罚、网络传播等规则。

常见类型包括：

```text
PoW：工作量证明
PoS：权益证明
PoA：权威证明
```

比特币使用 PoW。矿工通过计算竞争出块权，节点根据规则选择有效链。

以太坊现在使用 PoS。验证者质押 ETH，参与区块提议、验证和投票。如果验证者作恶，可能受到惩罚。

PoA 常见于测试链、联盟链或较中心化的网络。它依赖一组被授权的验证者出块。

对本书读者来说，不需要在这里深入共识算法。需要抓住的是：共识决定交易如何进入区块，也决定哪个区块历史被网络接受。

因此，链上数据分析不能脱离共识。确认数、最终性、区块重组，本质上都和共识有关。

## 9.9 链上数据和交易所数据有什么不同

交易所行情数据通常围绕价格、成交量和订单簿组织。

链上数据围绕区块、交易、地址、合约和事件组织。

两者差异很大。

| 维度 | 交易所数据 | 链上数据 |
|---|---|---|
| 基本单位 | 成交、订单、K 线 | 区块、交易、日志、状态 |
| 时间来源 | 交易所撮合时间 | 区块时间 |
| 数据稳定性 | 交易所接口返回后通常稳定 | 新区块可能存在重组风险 |
| 失败记录 | 普通下单失败不一定进入行情 | 失败交易可能上链并消耗 Gas |
| 成本字段 | 手续费、滑点 | Gas、协议费、滑点、MEV |
| 可见范围 | 交易所内部数据有限 | 链上公开数据较多，但需要解析 |

这就是为什么链上数据不能直接按交易所数据的思路处理。

例如，交易所里一笔成交就是一笔成交。DEX 中一笔交易可能经过多个池子、多个合约、多个内部调用，最后产生多个事件。

再比如，一笔链上交易失败，价格没有兑换成功，但 Gas 已经消耗。对策略收益来说，这仍然是成本。

## 9.10 链上数据分析最常见的误区

第一个误区，是把交易哈希当成交易成功。

交易哈希只能说明有这笔交易记录。要判断是否完成预期操作，还要看 `status`、事件日志和余额变化。

第二个误区，是只看 `to` 地址。

在合约交互中，`to` 通常是被调用的合约地址。真正的资产转移可能发生在事件日志里，也可能通过内部调用完成。

第三个误区，是把区块时间当成精确成交时间。

区块时间只能说明交易被打包所在区块的时间。它不等于用户点击确认的时间，也不等于交易在等待池中出现的时间。

第四个误区，是忽略失败交易。

失败交易没有完成预期操作，但可能已经消耗 Gas。做策略评估时，失败交易成本不能直接删除。

第五个误区，是把刚出现的数据当成最终数据。

新区块可能重组，索引服务可能延迟，区块浏览器显示也可能有同步时间差。越接近实时，越要处理不确定性。

## 9.11 从量化研究角度看本章

本章不是为了把读者变成区块链底层工程师。

它的作用是建立链上数据研究的最小准确模型。

后续做 Web3 量化研究时，会反复遇到这些问题：

```text
这笔交易是否成功？
它属于哪个区块？
区块是否已经足够稳定？
这笔交易调用了哪个合约方法？
它产生了哪些事件日志？
Gas 成本是多少？
它是真实用户行为，还是合约内部调拨？
它是市场信号，还是噪音？
```

这些问题回答不清楚，链上指标就容易失真。

例如，统计“某 Token 大额买入”时，不能只看 Token 转账金额。需要判断它是否来自 DEX 兑换、是否是交易所内部归集、是否是跨链桥铸造、是否是合约迁移。

链上数据公开，不代表链上结论简单。

## 9.12 本章实践

打开一个区块浏览器，任选一笔 EVM 链上的交易，记录以下信息：

```text
交易哈希：
所在链：
所在区块：
区块时间：
确认数：
交易状态：
from 地址：
to 地址：
这是一笔普通转账，还是合约交互：
是否有 input data：
是否产生事件日志：
Gas Used：
交易费用：
如果是 Token 转账，Token 合约地址是什么：
如果是 DEX 交易，是否能看出输入资产和输出资产：
```

再补充三个判断：

```text
这笔交易是否已经成功？
这笔交易是否已经足够稳定？
这笔交易能否作为量化数据样本使用？
```

如果暂时判断不了，就写“不确定”，并记录原因。

## 本章小结

区块链可以用“公共账本”入门，但更准确的理解是：它是一套由节点共同维护的、有顺序的、可验证的状态记录系统。

区块把交易和验证信息组织在一起。交易是经过签名的状态变更请求。共识机制让节点对链上历史和当前状态达成一致。

链上数据的难点不在于能不能看到，而在于能不能正确解释。交易哈希、区块高度、确认数、状态、事件日志和 Gas，都会影响数据含义。

对 Web3 量化研究来说，链上数据不是天然可用的信号。它需要确认、解析、清洗和分类。
